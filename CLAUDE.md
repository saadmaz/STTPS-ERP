## 2. Git and release rules (strict)

- Work on `develop`, commit there and push directly (`git push origin develop`). Never commit to `main`.
- Conventional commit messages: `feat(module): …`, `fix(…): …`, `chore: …`. One commit per finished item. Each commit must pass lint, typecheck, build and tests.
- **No AI attribution anywhere.** No `Co-Authored-By` trailers, no "Generated with…", no mention of Claude, Anthropic or AI in commits, PRs, comments or release notes.
- Never force-push and never rewrite history.
- Do **not** release after each item. When the whole plan is done, follow `docs/runbooks/release.md`: bump all three `package.json` versions, move the CHANGELOG `Unreleased` section, open one PR `develop` → `main`, **squash-merge it** (so no Dependabot co-author lines appear), tag it and publish the GitHub release.
- Dependabot is deliberately disabled. Fix vulnerable dependencies by hand. The push warning about vulnerabilities on `main` refers to the old tree and clears at release.
- After pushing, check CI with `gh run list --branch develop --limit 3`. If it is red, fix it before starting the next item.

## 4. API patterns (copy these, don't invent new ones)

**Best templates to copy:** `api/src/procurement/` (a full module: services, module, DTOs, models) and `api/src/finance/` (ledger postings, AR/AP, budgets, expenses, assets).

### Master data / documents
- Services extend `MasterDataService<Doc, CreateDto, UpdateDto>` (`platform/crud/master-data.service.ts`).
  - **Config:** `module`, `entity`, `label`, `collection`, `route`, plus optional `uniqueFields`, `references`, `parentField`, `filterFields`, `numbering` (`{ field, key, prefix, yearly }`), `large` (a `LargeListSpec` for big collections), `permission` (override) and `customFields`.
  - **Hooks:** `toNew` and `toPatch` map DTOs to documents. `validate` and `derive` are read phase. `beforeWrite` and `afterWrite` are write phase. Use `searchEntry` for global search.
  - **Pre-computing lines:** override `create`/`update` to do the reads outside the transaction (prices, products, rates), then pass the results through a `built` field on the DTO object. See `PurchaseOrderService` and `InvoiceService`.
- **Controllers:** `createMasterDataController({ path, tag, module, permission, service, createDto, updateDto })` gives list, get, history, create, patch (with `If-Match`), archive and restore. Extra actions go in a hand-written controller using `@RequireModule`, `@RequirePermission`, `@HttpCode(200)` on POST actions, and `@Body(validated(Dto))`.
- **Controller order:** list hand-written action controllers **before** the `...crud` controllers in `@Module({ controllers })`, so their literal routes win.
- Request context comes from `@Ctx() ctx: RequestContext`. For event handlers, build one with `systemContext(event, userId)`.

### Firestore transactions: the rule that causes most bugs
**All reads must happen before any write inside a transaction.** Every service that touches several documents uses a two-phase shape:
```ts
const plan = await this.ledger.prepare(tx, ctx, input, { withNumber: true }); // reads only
const approval = await this.prepareApprove(tx, ctx, before);                  // reads only
const request = await this.approvals.open(tx, ctx, prepared);                // reads, then writes
plan.commitNew(); approval.apply();                                           // writes only
```
- Never call `repo.get`, `tx.get`, `ledger.prepare`, `approvals.open` or `sequences.reserve` after a write in the same transaction.
- `approvals.prepare()` runs **outside** the transaction. Inside it, call `approvals.open(tx, …)`; if it returns `status === "approved"` (no workflow applies), apply at once, otherwise set `pending_approval`. Handle the result by subscribing to `APPROVAL_COMPLETED` in `onModuleInit`. Copy `PurchaseOrderService.submit` exactly.
- Two separate "prepare" helpers that both load the same document will overwrite each other's writes. If two changes touch one doc (for example stock on hand and on-order), make them one change. See `onOrderDelta` in `InventoryLedger.prepare`.

### Money, quantities, dates
- Money is **integer minor units** (cents). Quantities are **integer thousandths** (`QTY_SCALE = 1000`). Rates and percentages are **hundredths of a percent** (1800 = 18%).
- Use the helpers in `platform/data/money.ts`: `toMinor`, `fromMinor`, `toQty`, `extend(qty, unitPrice)`, `applyRate`, `allocate`. **Never use floats** for money.
- DTOs take money and quantities as **strings** (regexes `MONEY`, `QTY`), converted in the service.
- Dates are ISO strings `YYYY-MM-DD`; fiscal periods are `YYYY-MM`.
- Foreign currency: convert with `toBase(amount, rate, currency, base)` from `finance/ar.services.ts`. Rates are decimal strings looked up through `ExchangeRateService.rateOn`.

### Ledger postings
- Post only through `GeneralLedger` (`finance/ledger.service.ts`), either `prepare(...)` then `commitNew()`/`writeLedger()`, or `post()` in its own transaction. It checks fiscal periods, rejects group accounts and guards control accounts.
- Look up accounts by role with `ledger.account(settings, "receivable" | "payable" | "bank" | …)` (`POSTING_ROLES` in `finance.models.ts`). Never hard-code account ids.
- Automatic postings from events go through `AutoPostingService`. A failure becomes a posting issue, not an exception.

### Events and jobs
- Publish with `events.publish(tx, ctx, "PastTenseName", { entity, entityId }, payload)` inside the business transaction (transactional outbox).
- Subscribe with `events.subscribe(type, "module.uniqueName", handler)`. Handlers must be idempotent.
- `BACKGROUND_WORKERS` is off in tests; call `app.get(JobQueueService).drain()` to run handlers.
- There is no cron scheduler yet. Scheduled work is exposed as an explicit "run" endpoint (see recurring journals and the depreciation run).

## 5. Adding a new module: checklist

1. `api/src/<mod>/<mod>.models.ts`: `COLLECTIONS`, document interfaces, `LISTS: LargeListSpec` for large collections.
2. `<mod>.dto.ts`: class-validator DTOs (`PartialType` for updates).
3. `<mod>.services.ts` and `<mod>.module.ts`: import the modules whose services you need (`OrgModule`, `SalesModule`, `FinanceModule` …). Watch for import cycles.
4. `api/src/platform/modules/catalog.ts`: set `available: true` and add `permissions: [...entityPermissions(mod, entity, "label")]` plus any custom codes.
5. `api/src/app.module.ts`: add the module to `imports`.
6. `api/src/platform/data/indexes.ts`: add `largeListIndexes(...)` for large lists, plus explicit composite indexes for any query that combines equality with a range or order on another field. Then run `npm run indexes` (in `api/`) and commit the regenerated `firestore.indexes.json`. A test fails when they drift — and a second test, `test/platform/indexes.spec.ts`, hard-asserts the total stays at or under **200, Firestore's own real ceiling** (not a self-imposed one; an earlier version of this file, and of that test, guessed 180 and was wrong, which is itself what the Shifts and Leave items ran into before the test had to be corrected). **At 194/200 as of Phase 4 Support desk** — `CalendarEventDoc`, Maintenance's `WorkOrderDoc` and Asset audits/repairs were all kept on the small list on purpose (real, documented risk, not an oversight: see each one's plan entry) specifically to hold the line here; Support's `TicketDoc` was judged genuinely high-volume (customer-facing, comparable to Attendance/Tasks) and given `large`, which is what moved 192→194. With only ~6 left, **the next genuinely high-volume collection (one row per person per day/event, the pattern Attendance, Shifts, Leave requests, Goals/Reviews, Payslips, Tasks/time entries and now Tickets all turned out to follow) may not fit without dropping or consolidating something else first** — don't just reach for another `largeListIndexes` call; re-read this whole section, add up what's left, and raise the tradeoff explicitly before spending more. The actual rule for whether something needs `large` is the **parent-vs-per-event-child** distinction (Payroll runs vs. payslips; Projects/phases/milestones vs. Tasks), not "this module feels big" or "this cadence sounds slow". A single equality-only query (no range filter, no `orderBy`) needs no composite index at all — Firestore serves it from the automatic per-field indexes — so design hot lookups (like Attendance's "today's record for this employee") that way before reaching for another index.
7. Delete `api/legacy/<mod>` and `web/legacy/<mod>` if they exist.
8. Write `api/test/http/<mod>.spec.ts` (see §7).
9. Web: `web/src/modules/<mod>/`, pages under `web/src/app/(platform)/<mod>/`, and a section in `web/src/components/layout/Sidebar.tsx` with `module` and `permission` set.
10. Docs: tick the plan checkbox (with an *italic note* if partial) and add an `### Added` entry under `## [Unreleased]` in `CHANGELOG.md`, written for users.

## 6. Web patterns

- **Lists and records:** define a `MasterConfig<T>` (columns, filters, fields, title, subtitle, status, `editable`, `actions`, `details`, `extra`) and render it with `MasterListPage` / `MasterRecordPage` (`components/master/MasterData.tsx`). The record page already includes the Activity and Files tabs.
- **API clients:** `crud<T>(path)` from `lib/api.ts`. Show errors with `errorMessage(e)` and `toast`.
- **Action buttons:** `Action` from `modules/sales/config.tsx` handles a permission check, an optional confirm dialog with a reason, POST, then refresh. Use `ConfirmDialog` (`components/ui/kit.tsx`, which accepts `children` for extra fields) for small forms.
- **Permissions:** `useCan("module.entity.action")`; never show controls the user cannot use.
- **Formatting:** `formatMoney(minor, currency)` and `formatDate`. Quantities display as `n / 1000`.
- **React lint rules that fail the build:**
  - No `setState` inside `useEffect` to seed forms. Load the data in a parent, then render a child form that takes it as initial state through props (see `NewOrder` / `OrderForm` in procurement).
  - No impure calls in render or in `useState(value)`. Write `useState(() => new Date(...))`, not `useState(new Date(Date.now()))`.
- Dark mode: every colour class needs its `dark:` pair. Layouts must work at phone width.
- No browser is available here, so UI is verified by typecheck, lint and build only.
- **A genuinely separate auth surface (customer portal, and any future one like it) gets its own axios client**, not the staff `lib/api.ts` (`lib/portal-api.ts` is the template: its own token key, no `x-company-id`, no refresh-token interceptor) — and its own top-level route outside `(platform)`/`(auth)` (`app/portal/`, mirroring the already-existing public `app/q/[token]` pattern), not a page nested under the staff shell.

## 8. Environment gotchas (Windows)

- Prefer the **PowerShell** tool for npm, tests and git. The Bash tool is Git Bash: fine for `grep`, `sed` and `gh`.
- **`vitest run` crashes with `TypeError: Cannot read properties of undefined (reading 'config')` when run from Git Bash in this repo** (confirmed: happens even on a trivial spec, even with the `unplugin-swc` plugin removed, even after pinning `vite` down a major version — none of that was the cause, so don't re-chase it or touch `vite`'s version over this). The actual cause: Git Bash's `cd` reports the cwd with a lowercase drive letter (`c:/Work/...`), and vite's module runner on Windows gets tripped up resolving the built-in reporter module against that path. Run `vitest`/`npm test` via the **PowerShell** tool instead (its cwd is `C:\Work\...`, proper case) and it passes cleanly — don't spend time on this again.
- Bash heredocs containing backticks or `${…}` fail with "unexpected EOF". To make multi-line edits, write a Python script into the scratchpad with the Write tool and run `python <path>`, or use the Edit tool.
- Never write literal invisible characters (a BOM, for example) into source. Use escapes like `﻿`.
- Never kill processes broadly. If the emulator hangs, stop only the process on its port.
- Don't add `firebase-tools` as a dependency; it is pinned through `npx` in the test script.

Expense claims still key off the **user id** directly — leave that alone; payroll and self-service should resolve the employee from `userId`, not the other way round.
- **Sensitive HR fields:** `EmployeeDoc.compensation`, `bankDetails` and `nationalId` need `hr.employee.compensation`, checked in `EmployeeService` (read redaction in `get`/`list`/`history`, write guard in `toNew`/`toPatch`) — not the generic Phase 0 record-level-scope engine, which still doesn't exist. Copy this per-field pattern for other sensitive data before that engine lands.

- **Onboarding/offboarding (done):** `ChecklistService` (`api/src/hr/hr-onboarding.services.ts`) is deliberately standalone — no sibling HR service injected, just the generic `references` config on `employeeId` — specifically so `EmployeeService.terminate()` and `CandidateService.hire()` can both depend on it (one direction each) without a cycle. It auto-starts a checklist via `start()`, which is idempotent (reuses an in-progress one rather than throwing), called *after* the caller's own transaction commits, the same two-phase pattern as `hire()` creating the employee. The public career page pattern (`PublicCareersController`, no `@RequireModule`/`@RequirePermission`, just `@Public()`, scoped by raw `companyId` rather than a hashed token since the content is already public) is the template for any other public-facing portal.
- **Attendance (done):** `api/src/hr/hr-attendance.*` and `AttendanceService`/`DeviceService`/`AttendanceSettingsService` (`hr-attendance.services.ts`). The device-integration auth story: a kiosk credential distinct from a normal user session — `randomBytes(24).toString("base64url")` shown once, looked up by its SHA-256 hash as a Firestore doc id in `hrAttendanceDeviceKeys` (copied from `QuoteService`'s public quote-link token pattern), with `DeviceDoc.currentKeyHash` tracking the live one so issuing a new key retires the old lookup entry. `PublicAttendanceController` (`/public/attendance/clock`, `@Public()`) resolves the device by key, builds a `RequestContext` by hand (tenantId/companyId from the device, `allPermissions: true`), then resolves the employee by `employeeNumber` (QR) or `employeeNumber` + PIN (bcrypt-hashed on `EmployeeDoc.attendancePinHash`, stripped from every response like a password). Signed-in web/mobile clock-in goes through `AttendanceSelfServiceController` (`/hr/attendance`, no `@RequirePermission`) instead, resolving the caller's own employee via `EmployeeService.findByUserId`. Late/early/overtime are computed against one company-wide standard shift (`AttendanceSettingsService`), not per-shift schedules — that is Shifts' job once built. Firestore index cost: the one `large:` list config for `hrAttendanceRecords` also serves the hot "today's record for this employee" lookup (pure equality, no composite index needed) and the timesheet range query, so no indexes beyond the standard pair were needed.
- **Shifts (done):** `api/src/hr/hr-shifts.*` and `ShiftTemplateService`/`ShiftAssignmentService` (`hr-shifts.services.ts`). A `ShiftAssignmentDoc` snapshots its template's `startTime`/`endTime`/`isNightShift` at creation time (the "pre-computing lines" pattern — read the template outside the transaction in `ShiftAssignmentService.create()`, pass it through a `built` field, copied from `PurchaseOrderService`), so a later template edit never changes a shift already assigned. A swap is a `SwapRequest` stored on the requesting assignment (`swap` field), decided by HR in `decideSwap()`: on approval, a single transaction reads both assignments first, then writes both, exchanging their `employeeId` and setting `status: "swapped"` on each — the usual "all reads before any write" rule, same shape as Attendance's `clockOut`. **Not done:** Attendance's late/early/overtime still read the one company-wide `AttendanceSettingsDoc` rather than each employee's actual assigned shift for the day — hooking that up (resolve a `ShiftAssignmentDoc` for the date in `AttendanceService.clockIn`/`clockOut` instead of the shared setting) is real follow-up work, not done here to avoid touching already-shipped, tested Attendance code under one more item's scope. "Rotating shifts" is served by assigning different templates on different dates by hand; there is no recurrence/roster generator.
- **Leave (done):** `api/src/hr/hr-leave.*` and `LeavePolicyService`/`HolidayService`/`LeaveBalanceService`/`LeaveRequestService` (`hr-leave.services.ts`). `LeaveBalanceDoc` is deliberately not a `MasterDataService`/`BaseDoc` — it's current state at a deterministic id (`${employeeId}_${policyId}`), the same shape as `AttendanceSettingsDoc`, updated via `LeaveBalanceService.applyUsage`/`releaseUsage` inside the same transaction as the request's own status change (read the request, the policy and the balance — creating a blank in-memory balance if none exists yet — before any write, then write both). `rollover(ctx, year, employees, policies)` iterates every employee × policy with its own read-then-write, not one giant transaction (the depreciation-run shape), and is idempotent per pair (skips a pair already at the target year). **Not done:** `AttendanceService.markAbsent` and Leave stay unconnected — marking a day absent in Attendance doesn't check or consume a leave balance, and approving leave doesn't create an Attendance record — wiring that is real follow-up work. Monthly accrual is not automated (see the plan's scope note).
- **Performance (done):** `api/src/hr/hr-performance.*` and `PerformanceCycleService`/`GoalService`/`ReviewService`/`DevelopmentPlanService` (`hr-performance.services.ts`). A self-review is upserted — `ReviewService.submitSelfReview` looks for the employee's own existing "self" review for the cycle and updates it while still a draft, rather than ever risking a duplicate; `aboutMeSubmitted` filters to `status: "submitted"` so a manager's or peer's unfinished draft never leaks to the employee it's about. `GoalService`/`ReviewService.create()` both guard on `PerformanceCycleDoc.status !== "closed"` before writing. **Not done:** no record-level scope means anyone with `hr.review.edit` can author a "manager" review for anyone, not just their own reports — the same project-wide gap noted in §10; no aggregated/weighted score from goal weights into a review's rating.
- **Employee self-service (done):** `api/src/hr/hr-selfservice.*` and `AnnouncementService`/`HrRequestService`/`EquipmentRequestService` (`hr-selfservice.services.ts`), plus `EmployeeService.updateOwnProfile` and `UpdateMyProfileDto` (`hr.dto.ts`) for the "allowed personal updates" piece. `UpdateMyProfileDto` only declares `phone`/`address`/`emergencyContact` — the self-service PUT can never reach `status`, `compensation` or any other employee field, because `validated()`'s `forbidNonWhitelisted: true` rejects any extra property in the request body outright (the same mechanism that caught the `MarkAbsentDto` bug in Attendance; here it's relied on deliberately as the safety net, not worked around). Equipment requests are approval/bookkeeping only — no real asset to allocate, since there's still no asset register. **Not done:** payslips (needs Payroll) and expenses self-service wasn't added here since it already existed from Phase 2 (`/expenses`); "My HR" links out to the separate My Attendance/Shifts/Leave/Performance pages rather than consolidating them.
- **Payroll and the Sri Lanka statutory pack (done):** `api/src/hr/hr-payroll.*` and `StatutoryRateService`/`ApitBracketService`/`SalaryComponentService`/`SalaryStructureService`/`LoanService`/`PayrollRunService`/`PayslipService` (`hr-payroll.services.ts`). Five new `PostingRole`s (`salaryExpense`, `employerStatutoryExpense`, `payrollLiability`, `statutoryPayable`, `payrollTaxPayable`, `employeeLoans`) were added to `finance/finance.models.ts`'s `POSTING_ROLES`/`STANDARD_CHART` — two brand-new accounts (`1250` Employee loans and advances, `6110` Employer statutory contributions) and three existing ones newly given a `role` (`2400`, `2410`, `2420`). `HrModule` now `imports: [FinanceModule]` to inject `GeneralLedger` (the same cross-module pattern `finance/expenses.ts` already used, just across a real module boundary this time — check `app.module.ts`'s import order before adding another such dependency, to avoid a cycle). **Loan disbursement posts to the GL, not just an HR record** — this is easy to miss and easy to get wrong: without debiting the `employeeLoans` asset account when a loan is granted, a payroll run's installment recovery would credit that account with nothing to balance against. A payslip's APIT uses the published per-band "`income × rate − subtract`" formula (`ApitBracketDoc`), not hand-rolled marginal banding. The hand-worked example in `hr-payroll.spec.ts` is the reference for anyone checking this math; it also covers the GL balance after locking, a whole-period unpaid-leave deduction producing a negative net pay that blocks approval, and a loan's disbursement-and-recovery round trip.
- **Payroll lives under the `hr` module, not a separate `payroll` one.** An earlier version of `catalog.ts` had a leftover `mod({ key: "payroll", ... available: false })` stub from before Payroll was built; it was dead (every payroll controller actually uses `@RequireModule("hr")`) and has been removed. If a `payroll` module key ever reappears, that's a sign something regressed, not a feature to wire up.
- **Projects and Tasks (done):** `api/src/tasks/` (`TaskService`, `TimeEntryService`) and `api/src/projects/` (`ProjectService`, `ProjectPhaseService`, `MilestoneService`, `ProjectCostService`). Both share the catalog's existing `projects` module key (its description already said "Projects, tasks, time tracking and project billing" before either was built). `TaskDoc` is deliberately one entity for both a personal My Work task and a project task (`projectId` nullable) — don't build a second task type for Projects. Tasks has no per-entity permission scaffolding (no `entityPermissions()` calls) — it's ownership-gated instead (owner, assignee or collaborator, or the `tasks.allTasks.view` permission for oversight); `TaskActionsController`/`TimeEntryActionsController` are hand-written rather than `createMasterDataController`, which is why. Completing a recurring task's side effect (creating the next occurrence) lives in `TaskService.setStatus`, not in `toPatch` — status changes go through a dedicated action, not the generic PATCH, for exactly that reason (same pattern as Attendance's clock actions and Leave's decide/cancel).

If that's ever wired up for real, don't make `MaintenanceModule` depend on `InventoryModule`'s `AdjustmentService` directly (it has its own draft→approval→post lifecycle built for manual stock corrections, not a good fit) — model it as its own movement type in `InventoryLedger` instead, the way Sales/Procurement each post their own movement types without going through Adjustments.
- **Asset management (done):** extends the existing `finance/assets.ts` (`FixedAssetService`) in place — `AssetDoc` gained `warrantyExpiryDate`, `condition`, `checkedOutTo`/`checkedOutAt`/`dueBackDate` (a short-term loan, separate from the long-term `custodianId`) and `isMissing`/`missingSince`, plus `checkOut`/`checkIn`/`reportMissing`/`recoverFound` methods and matching `AssetsController` routes. New audits and repairs live in a sibling file, `finance/asset-audits.ts` (`AssetAuditService`, `RepairService`), the same "split by sub-concern within one module" pattern as `hr-attendance.services.ts` next to `hr.services.ts`. **If you ever need to validate `custodianId`/`checkedOutTo` against a real employee, don't add an HR dependency to `FinanceModule`** — `HrModule` already imports `FinanceModule` for `GeneralLedger`, so the reverse would cycle; do any such validation from a module that can see both (the way `CalendarModule` does), not from within `assets.ts` itself. The web's QR label (`web/src/modules/finance/assets.tsx`) added the `qrcode` npm package (and `@types/qrcode`) — the only new frontend dependency Phase 4 has needed so far; it renders client-side from the asset's own code, nothing server-side to maintain.
- **Calendar (done):** `api/src/calendar/` (`CalendarEventService`, `CalendarService`). `CalendarModule` imports `HrModule`, `TasksModule` and `ProjectsModule` directly (not just their individual services) specifically to reach `EmployeeService`/`ShiftAssignmentService`/`LeaveRequestService`, `TaskService` and `MilestoneService` for the aggregator — the heaviest cross-module `imports:` graph in the codebase so far; if Calendar ever needs to depend on something new, check for a cycle against all three first. `CalendarService.company()`'s per-section permission check (`hasPermission(ctx, "hr.shiftAssignment.view")` etc. gating whether that section is included) is a **graceful-degradation** pattern worth reusing: the endpoint itself carries no permission wall, callers just see less. A recurring event's occurrences are computed on request (`expandOccurrences`, capped at 366 steps) rather than materialised as documents — don't add a "generate occurrences" job or endpoint, there's nothing to generate. Google/Microsoft sync is not built (see the plan entry for why) and Google/Microsoft Calendar API knowledge is not assumed anywhere in this codebase yet.
- **Support desk and Customer portal (done):** `api/src/support/` (`SlaPolicyService`, `TicketService`, `PortalUserService`, `PortalAuthService`). `TicketDoc` is `large` (customer-facing, high-volume — see §5); every status-changing action (`assign`/`reply`/`status`/`escalate`/`merge`/`reopen`/`rate`) is a dedicated method, never a bare PATCH, the same reasoning as Leave's `decide`/`cancel` and Tasks' `setStatus`. SLA due dates are plain calendar-time addition from `SlaPolicyDoc.targets`, computed once in `TicketService.create()` — **not business-hours- or holiday-aware**, a real gap (see the plan entry), since there's no working-calendar concept anywhere yet to hang that off. `CreateSlaPolicyDto.targets` is optional (defaults to `DEFAULT_SLA_TARGETS` in `support.services.ts`) specifically so the staff UI can create a policy from a simple form and edit targets afterwards in a dedicated table — `MasterConfig.fields` has no array-of-object input type, so don't try to cram a `targets[]` editor into the generic create form for anything like this; give it its own small `extra()` panel instead (`SlaTargetsEditor` is the template).
  - **The portal auth design, worth re-reading in full before touching anything here:** `PortalUserDoc` lives in its own collection (`supportPortalUsers`), never `users` — a portal id essentially can't collide with a staff one even by accident. On top of that, `JwtPayload` gained an optional `scope` field and `JwtStrategy.validate()` (`api/src/auth/strategies/jwt.strategy.ts`) throws if it's set, mirroring the existing `purpose` (MFA step token) rejection — so a portal token is rejected by every staff route independent of the separate-collection lookup ever missing. Portal tokens are signed by the *same* `JwtService` (`SupportModule` imports `AuthModule`, which `exports: [AuthService, JwtModule]` for exactly this), just with `scope: "portal"` and a 24h expiry (no refresh — a documented, deliberate scope reduction from staff's 15-minute-plus-refresh). `PortalAuthGuard` (in `support.module.ts`, not a Passport strategy) verifies the token by hand and attaches `request.portalCtx`; every portal controller is `@Public()` with no `@RequireModule`/`@RequirePermission`, so the four global guards (`JwtAuthGuard`, `CompanyContextGuard`, `ModuleGuard`, `RequirePermissionGuard`) all no-op on them (each one specifically checks for `!user`/`!key`/`!required` — re-read their source before assuming a new public controller is safe without checking this) and `PortalAuthGuard` is the only real check. No self-registration: `PortalUserService.provision()` (admin-only) mints a one-time setup token the same way `QuoteService.send()` and Attendance's device keys do — `randomBytes(24).toString("base64url")` shown once, looked up by its SHA-256 hash as a doc id in `supportPortalSetupTokens` — and the identical token/lookup mechanism serves a forgotten-password reset (`reissueSetupToken`), so there's no separate email-based reset flow to build or keep in sync. **If you extend the portal to a new module (orders, invoices, documents), follow this exact shape** — own collection or a customer-scoped query, a dedicated guard/ctx decorator if the existing `PortalAuthGuard`/`PortalCtx` don't already cover it, ownership checked in the service (not just the controller) the way `TicketService.getOwn`/`rate`/`reopen` check `customerId` — rather than reusing any staff-side permission check for it.
- **Document management (done):** `api/src/documents/` (`DocumentFolderService`, `DocumentService`). Deliberately thin, and the thinness is the point: `DocumentDoc` holds metadata and lifecycle only. The actual file, its versions, download and preview are the **existing generic Files feature** reused as-is (`entityType: "documents.document"` against `/files/upload-url`, nothing Documents-specific needed); linking a document to the record it's about is the **existing generic related-records feature**, not a new field pair — don't add `linkedEntityType`/`linkedEntityId` or any other bespoke link if you extend this, use `/records/:type/:id/related`. Approval reuses `ApprovalsService.prepare`/`open` exactly the way Quotes/Price lists do (`DocumentService.submitForApproval`, auto-approves with no workflow configured for `documents.document`) plus the matching `onModuleInit` subscriber to `APPROVAL_COMPLETED` (named `"documents.documentApproval"` — event handler names are global and unique across the whole app, check `grep -rn APPROVAL_COMPLETED` before picking one). E-signature is a real adapter interface (`ESignatureProvider`, `api/src/documents/signature-provider.ts`) with one implementation, `ManualSignatureProvider` — it doesn't call anything external, `recordSignatureOutcome` is always how the result gets in, by design (no provider here has a webhook yet). "Create from template" (`createFromTemplate`) copies metadata only, not the file — there's no generic "copy a file between records" operation to call for that; document the gap again if one ever gets built rather than silently fixing it here. Expiry is a stored date with nothing watching it (same "no cron yet" gap as Calendar reminders and Payroll); the web list computes "Expires in Nd" client-side, the same pattern Support's SLA countdown already established (`dueLabel`/`expiryLabel` are the same idea under different names — don't be surprised they're not shared, this codebase doesn't have a cross-module web utility file for that kind of thing yet).

## 10. Review hotspots (for a later review by a stronger model)

Areas where subtle errors are most likely and that deserve a careful second look:
- **Transaction ordering** (reads before writes) in every service with `prepare*` / `apply`, especially new code.
- **Ledger correctness:**
  - **Balanced entries:** `GeneralLedger.normalise` throws on unbalanced journals, but the sign conventions in AR/AP/bank/asset postings deserve checking.
  - **FX differences** in receipts and payments.
  - **Disposal gain or loss.**
- **Three-way match** (`finance/ap.services.ts`, `matchBill`) and the commitments in budget control (`finance/budget.ts`).
- **Concurrency on hot documents:** stock summaries, GL monthly balances, sequences.
- **Access control:** the catalog permissions on every route. Record-level scoping (Phase 0 open item) is not done: for example, any user with `expenses.claim.view` sees all claims, and any `hr.employee.view` holder sees every employee (just not their compensation).
- **Sensitive-field redaction:** `EmployeeService`'s compensation masking is hand-written per field; check it stays in sync if `EmployeeDoc` grows more sensitive fields, and that no new read path (reports, exports, search) bypasses `get`/`list`/`history` and reads the collection directly.
- **Payroll statutory calculations** (once built).
- **The customer-portal authentication boundary** (`api/src/support/`): the `scope: "portal"` JWT claim rejection in `JwtStrategy.validate()`, `PortalAuthGuard`'s manual token verification, and every portal-facing route's ownership check (`customerId` matched against the token's, not just against the request body) — a mistake here crosses a real trust boundary (an external customer, not just a different internal permission level), so it deserves a dedicated look rather than being folded into the general access-control sweep above.
